## 3. 当前配置的 4 个真实缺陷（都有实测证据）

### 3.1 ★ 致命：`authorizationUri` 缺 `redirect_uri`

当前 URI 只有 3 个参数：`client_id` / `response_type` / `scope`，**没有 `redirect_uri`**。

只读探测对照（未登录态，跟随跳转）：

| 构造 | 结果 |
|---|---|
| 无 `redirect_uri` | HTTP 200，但页面内容为「**redirect_uri 请求不合法**」 |
| 带 `redirect_uri=https://vertexaisearch.cloud.google.com/oauth-redirect` | 正常跳转 `accounts.feishu.cn/accounts/page/login?...`（92 KB 登录页） |

对比参照：`ge-nexus-lark-1..4`（并行项目那 4 批）**都带** `redirect_uri=https://vertexaisearch.cloud.google.com/oauth-redirect`。

→ **结论：本项目当前授权流程走不通。这解释了「表面出现授权不通」。**

> 更正：我在 2026-10-30 上一轮曾以「issue #3274 记录用户看到过 popup」为由**撤回**这条判断。现在有了 `authorize` 端点的直接对照实验，该撤回是错的 —— **缺 redirect_uri 确实会让授权页报错**。当时那条 issue 属别的项目/别的 URI 配置，不能用来否定本项目的实测。

### 3.2 覆盖不足：22 / 173

- 当前唯一 scope 29 项，其中**只有 22 项属于 user 态**（另 7 项见 3.4）。
- 注册表 497 条命令里：**180 条**所在域有 user 态权限覆盖（base / calendar / docs / drive / im / wiki 六个域）；**317 条**所在域**完全没有**。

**但「域有覆盖」≠「命令能用」** —— 现有 22 项在域内是残缺的：

| 域 | 现有 user 权限 | 明显缺失 |
|---|---|---|
| drive | 仅 `drive.metadata:readonly`、`export:readonly` | 上传 / 下载 / 搜索 / 删除（`drive:drive` 是 tenant-only，用户态拿不到） |
| base | 仅 `table` / `record` 的 read+update | 建表、建字段、删记录 |
| im | 仅 `im:message` | 群管理（`im:chat` 是 tenant-only） |
| wiki | 仅 `wiki:wiki:readonly` | 创建/编辑知识库节点 |
| docs/docx | `content:read`、`media:download`、`import`、`export`、`docx:document` | 评论、权限设置写 |

→ 实际「能正常跑通」的命令面**显著小于 180 条**。

`apps` 域另有 79 条命令，但该域多数是应用管理接口，本就偏 tenant 身份，不宜计入用户授权缺口。

完全无 user 态覆盖的域（命令数）：`apps 79`、`sheets 52`、`mail 49`、`okr 27`、`task 21`、`event 16`、`approval 14`、`vc 13`、`api 11`、`minutes 11`、`slides 8`、`markdown 5`、`contact 4`、`mindnotes 3`、`note 2`、`whiteboard 2`。

### 3.3 重复 scope：2 项

`docx:document`、`im:message` 在 URI 的 `scope=` 中各出现 **2 次**（31 条 → 唯一 29 条）。
→ 飞书对重复 scope 报 `20067`。**未登录态探测未能复现**（页面不校验 scope），但去重是零成本，必须做。

### 3.4 混入 7 项「仅 tenant」scope

当前 29 项里有 **7 项 `token_types=["tenant"]`**，它们被放进了**用户授权** URL：

```
bitable:app
drive:drive
drive:drive.search:readonly
drive:drive:readonly
im:chat
im:message.group_msg
wiki:wiki
```

→ 在用户授权 URL 里请求 tenant-only 权限，属 `20068`（传了用户无法授权的 scope）风险；且它们**不提供任何用户态能力**（这解释了为什么 `drive`/`im` 域看起来「有权限」却仍无法执行写操作）。**同样未能在未登录态复现**，但应当剔除。

### 3.5 关于「scope 单次上限 ~50」

- 官方文档：200。
- 并行项目实测：~50（其 4 批按 45 设计且线上可用）。
- **我的探测无法证实也无法否证**：未登录态下 31 / 45 / 50 / 55 / 60 / 80 / 100 / **173** 全部正常进入登录页 —— 说明**数量校验发生在登录之后**，curl 测不出上限。
- 因此保留 **45/批** 的保守设计（有他人项目线上可用作为背书），并在真机验证阶段复核。

## 6. 落地建议：两阶段（实际执行选择 Phase 2 全量，见 §8）

### Phase 1（低风险、立刻恢复可用）

**只重建 1 批 = B1（45 项）**，同时修掉 3.1/3.3/3.4 三个结构缺陷：

- 加 `redirect_uri=https://vertexaisearch.cloud.google.com/oauth-redirect`
- 加 `prompt=consent`（确保每次都返回 refresh_token）
- 去重、剔除 7 项 tenant-only
- 补 `offline_access`（已有）

收益：用户**只授权 1 次**；文档/知识库/云空间（最常用）全部可用；授权流程从「必然失败」变为可用。
代价：sheets/mail/task/okr/vc/approval/slides 等仍不可用。

落地方式二选一：
- **A. PATCH 现有资源**（`ge-nexus-agent-oauth-id-gb-dev-guyue`）→ 资源名不变，agent 绑定不用改；但 URI 变了，已授权用户需**重新 consent**。
- **B. 新建 `ge-nexus-feishu-1` + 更新 agent 绑定** → 更干净，便于日后扩批；但需同步改引擎 env 并重新部署。

### Phase 2（全量，需要改代码）

绑定 B1..B4 四条 → 173 项全覆盖，**代价是用户首次使用要连续授权 4 次**，且必须改代码支持多 auth_id（见 §7）。

> 若追求「一次授权全覆盖」，只有降低诉求（B1 单批）这一条路 —— 173 项无法塞进一批。

        "projects/839062387451/locations/global/authorizations/ge-nexus-feishu-1",
        "projects/839062387451/locations/global/authorizations/ge-nexus-feishu-2",
