# 非流式与慢问题 · 解决方案（结合本项目 + 最新 SDK 调研）

> 调研日期：2026-10-26。前置阅读：`docs/GE流式与延迟问题核查报告.md`（问题根因的证据链）。
> 本文回答两个问题：① 结合本项目代码，非流式和慢具体怎么解决；② Python SDK 是否应当升级到最新版。

---

## 一、结论速览

| 问题 | 结论 |
|---|---|
| 非流式怎么解决 | 在 `deploy.py` 子类化 `AdkApp` 重写 `streaming_agent_run_with_events`，注入 `RunConfig(streaming_mode=StreamingMode.SSE)`。**升级 SDK 解决不了**（见第二节实测） |
| 慢怎么解决 | `agent_engines.create()` 补扩缩容参数（`min_instances` / `container_concurrency=36` / `resource_limits`）+ 模型 global 端点 + `thinking_level` 调低。已有部署可用 `agent_engines.update()` **免重部署直接改参数** |
| 是否升级 ADK 到 2.13.0 | **现在不升**。迁移成本高（Workflow Runtime 图引擎、Event schema、存储不兼容），且对本问题零收益。单独立项规划 |
| 是否升级 aiplatform 到 2.6.0 | **不升**。官方明确警告"固定 < 2.0.0"（模块重构 + agent_engines 更名在即）。但**必须**把 `>=1.135.0` 固定为精确版本（当前最优先事项） |

## 二、最新 Python SDK 调研结论（2026-10-26 实查）

### 2.1 版本现状

| 包 | 本项目（uv.lock） | PyPI 最新 | 差距 |
|---|---|---|---|
| google-adk | **1.24.1**（== 固定 ✅） | 2.13.0（2026-10-23 发布） | 跨越大版本：2.0 GA 于 2026-05-19 |
| google-cloud-aiplatform | 1.136.0（**pyproject 为 `>=1.135.0` ⚠️ 未固定**） | 1.x 线：1.165.1；总最新：2.6.0 | 云端构建每次拉最新，与本地漂移 |
| cloudpickle | 3.1.2（仅锁文件，pyproject 未显式声明 ⚠️） | — | 需在 pyproject 显式固定 |
| google-genai | 1.62.0（`>=1.56.0`） | — | 低风险，暂可不动 |

### 2.2 ADK 2.x 是什么量级的变更（升级成本评估）

ADK 2.0（2026-05-19 GA，要求 Python 3.11+）不是常规升级，官方迁移文档列明四类破坏性变更：

1. **Workflow Runtime 图执行引擎**：从层级 Agent 树改为图执行模型，Agent/Tool/Function 都是图节点；
2. **Event schema 变更**：新增 `node_info`、`output` 字段——自定义 SessionService 的刚性数据库表结构必须迁移（JSON blob 存储可豁免）；
3. **BaseAgent 改为继承 BaseNode**：1.x 的 `_run_async_impl()` 等自定义覆盖**被静默忽略**（不报错），需改用 Before/AfterAgentCallback；
4. **存储不兼容**：官方明确警告 2.0 会话数据与 1.x 数据库不兼容（且 2.0 仅向后兼容 1.28+ 会话，本项目 1.24.1 连这个基线都不满足）。

对本项目的具体影响：`nexus_agent/` 的工具层、`cli_client` 子进程沙箱、命令自省 Prompt 均基于 1.x 执行模型构建，需全面回归。

### 2.3 关键判定：升级解决不了非流式（三版本模板实测）

| 模板来源 | `streaming_mode`/`StreamingMode` 出现次数 |
|---|---|
| 本地 1.136.0（`.venv` 实查） | 0 —— 从不启用 SSE |
| **1.165.1（1.x 线最新，本次下载 wheel 实查）** | **0** |
| 2.6.0（总最新，本日早前 wheel 实查） | 0 |

且 ADK 2.x 中 `RunConfig`/`StreamingMode` 语义不变（`NONE` 仍是默认，SSE 仍需显式开启）；ADK 2.x 官方 `adk deploy agent_engine` 底层仍是 AdkApp 打包。**结论：任何版本组合下，GE 的 `:streamQuery` → `streaming_agent_run_with_events` 链路都不会自发流式，必须自行注入 SSE 配置。**

### 2.4 aiplatform 2.x 的官方警告

PyPI 页面官方原文：agent_engines 模块将在下一个大版本更名为 runtimes（sessions/sandboxes/memory_banks 移至顶层 client），**"To avoid unexpected updates, pin the SDK version to < 2.0.0"**。同时生成式 AI 模块（`vertexai.generative_models` 等）已于 2026-06-24 移除，agent 能力正在拆分到独立的 `google-cloud-agentplatform` 轻量包。2.x 处于架构换轨期，生产项目不宜跟进。

## 三、版本策略建议

1. **`pyproject.toml` 固定（立即做，唯一必做项）**：

```toml
dependencies = [
    "google-adk==1.24.1",
    "google-cloud-aiplatform==1.136.0",   # 从 >=1.135.0 改为精确锁定（与 uv.lock 一致）
    "cloudpickle==3.1.2",                  # 显式声明
    ...
]
```

   理由：官方最佳实践要求本地与云端版本**完全一致**以避免反序列化开销；当前开放下限意味着每次部署云端可能拉 1.165+/2.x，模板行为漂移会直接击穿第四节的流式改造。选 1.136.0（而非追新 1.165.1）是因为它已通过本项目 76 项测试与线上验证，锁定后如需升级再单独验证。

2. **ADK 2.x：暂不升级，单独立项**。收益（图工作流、Task API）与本问题无关；成本（迁移 + 回归 + 存储隔离）高。建议关注官方 1.x 维护窗口，在业务低峰期按官方迁移清单（schema → callback → yield → 异常处理审计）规划。

## 四、实施路径（按顺序）

### 第一步：固定版本（见第三节，改 pyproject 后 `uv lock` 重新生成）

### 第二步：治"慢"—— `deploy.py` 补部署参数（零风险，纯配置）

`agent_engines.create()` 支持 `min_instances / max_instances / resource_limits / container_concurrency`（1.157+ 参考文档确认；本地 1.136 已支持，升级锁定版本不影响）。修改 `deploy.py:144`：

```python
remote_app = agent_engines.create(
    agent_engine=app,
    requirements=requirements_source,
    extra_packages=[AGENT_WHL_FILE_NAME],
    display_name=os.getenv("AGENT_DISPLAY_NAME", "WebEye Nexus Agent"),
    min_instances=int(os.getenv("AGENT_MIN_INSTANCES", "1")),   # 上限 10；按基线并发设
    container_concurrency=36,                                    # ADK 异步 Agent 官方建议（9 的倍数）
    resource_limits={"cpu": "4", "memory": "8Gi"},               # 默认 4/4Gi，防高并发 OOM
    env_vars={...},  # 原有内容不变
)
```

**已有部署可免重部署**：`agent_engines.update(resource_name=..., min_instances=..., container_concurrency=..., resource_limits=...)` 支持对现有实例单项修改（官方参考文档确认），适合先在线上灰度验证效果。

模型调用改 **global 端点**（收益是可用性/减少 429，注意官方提示单次延迟可能略增）：将 Gemini 调用位置配置为 `global`。

### 第三步：治"非流式"—— 子类化 AdkApp 注入 SSE

在 `deploy.py` 中新增（模板源码以**锁定的 1.136.0** 为准：`.venv/lib/python3.14/site-packages/vertexai/agent_engines/templates/adk.py:1143` 的 `streaming_agent_run_with_events`，复制其完整实现，仅改 `run_async` 一处）：

```python
from google.adk.agents.run_config import RunConfig, StreamingMode

class StreamingAdkApp(agent_engines.AdkApp):
    async def streaming_agent_run_with_events(self, request_json, **kwargs):
        # ... 复制模板原实现：解析 request_json、获取/创建 session ...
        run_config = RunConfig(streaming_mode=StreamingMode.SSE)
        async for event in runner.run_async(
            user_id=..., session_id=..., new_message=...,
            run_config=run_config,          # 唯一改动点
        ):
            yield self._convert_event(event)  # 沿用模板的事件转换
```

并将 `deploy.py:115` 的 `agent_engines.AdkApp(...)` 替换为 `StreamingAdkApp(...)`。

**同一注入点可顺带治两项"慢"**：
- 会话历史裁剪：`run_config` 同处可设 `get_session_config`（`num_recent_events=...`），避免长会话每轮全量加载；
- 部署后先在 **GE 界面用长回答实测**：确认 partial 事件正常渲染、无重复显示（历史 bug adk-python#7395，修复 PR 尚未合并）。

### 第四步：模型层调优（低成本补充）

- `thinking_level` 调低档位（当前未配置 = 默认思考；`gemini-3` 系用 `thinking_level`，**不要用已弃用的 `thinking_budget`**）；
- 系统 Prompt 前缀保持稳定，提升隐式上下文缓存命中率；
- 中期精简 `discover → get_spec → execute` 高频路径的往返次数（见核查报告方案 C）。

## 六、风险与回滚

| 风险 | 缓解 |
|---|---|
| GE 前端流式渲染异常（重复显示） | 实测不通过即回滚：`deploy.py` 换回 `AdkApp` 重新部署（改造是纯增量，一行切换） |
| `container_concurrency=36` 内存压力 | `resource_limits` 已同步调高；观察 Cloud Logging OOM 日志，必要时降为 18 |
| 未来 aiplatform 升级导致模板漂移 | 版本已精确锁定；升级时需重新 diff 模板源码再改子类 |
| ADK 2.x 迁移冲动 | 与本解耦：所有改造基于 `RunConfig`（2.x 语义不变），未来迁移后子类代码可平移 |
